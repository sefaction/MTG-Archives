# Upload storage failure boundaries (#305)

This test-only batch follows the live P3 remaining storage gate. Existing unit tests cover immutable file writes, format/size/path/integrity checks; the photo database verifier covers a finalize-transaction fault. The new control composes the actual upload POST handler, actual private file writer and actual acquisition store against the existing guarded disposable PostgreSQL database.

Four deterministic boundaries run on tiny owned files: low free-space admission, ENOSPC after a real partial temporary write, EIO before atomic hard-link publication and EIO at directory sync after complete publication. The adapter forwards every other filesystem operation. It does not fill a disk, kill a host or claim natural filesystem failure reproduction. Authentication supplies the explicit owned actor; authorization/origin middleware is not qualified by this adapter.

For each actual failed response, the original upload identity has exactly one non-READY photo with null readyAt and no artifact, candidate or processing job. Temporary parts must be absent. Before publication the final file must be absent; after publication its complete bytes must match the original digest while the database remains non-READY. A same-key/slot/generation retry and lost-ACK replay must acknowledge the original photo exactly once, retain exact bytes and produce one candidate/artifact/canonical job. Detailed injected failures must not appear in the client response. Owned Inventory must be identical. Each fixture is cancelled through the ordinary store before later queue tests; parent database cleanup owns its graph and the scoped temporary root is removed in finally.

Exact-head execution is pending. This adds no product/schema change and does not establish true disk exhaustion, power-loss durability, concurrent retention/backup races, capture-consistent restore, mobile-device acceptance, sustained load or named installation deployment. Those remaining gates keep #305/#310 open. Local heavy work remains reserved under the existing runtime owner; no shared laptop or production data is accessed.
