# Public issue intake and joint review

Public submission needs a title and one description in the reporter's own words. The optional details box can hold reproduction, expected behavior, screenshots or environment. Users do not need to understand labels, roadmap hierarchy, work done/remaining or acceptance criteria. The general form is the fallback when they are unsure. Maintainers gather any missing context through focused conversation.

## Origin is separate from readiness

Brian and ChatGPT may use the same GitHub account. An author login, bot identity, polished prose, labels (including `codex`) or an issue-body declaration cannot establish whether ChatGPT filed an issue. Do not exclude Brian's hand-written issues from joint review because they look like internal work or have been assigned to a worker.

For a newly agent-created issue, the creating worker must retain an explicit creation receipt in its worker-controlled checkpoint/journal as part of the authorized creation operation. Record repository, returned issue node ID and number, creation timestamp, worker run/thread identifier and task/authorization reference. Preserve the creation operation's returned identity/readback, rather than manufacturing a receipt later from the issue's current body or labels. Receipts contain no credentials. An optional visible origin note can link the worker/run evidence, but the note alone is not verification.

A reviewer correlates the receipt with the issue's immutable identity and creation metadata and the named trusted worker record. Missing, inaccessible, mismatched or conflicting evidence means **unknown origin**, not agent-origin. This batch defines that protocol; it does not backfill old receipts, add a provenance service or claim the recurring reviewer already implements receipt verification. Existing historical records may be used only when they establish creation, not merely later work on the issue. Human and unknown-origin requests share the joint review path. Enriching a human issue never changes its original human origin.

`triage: complete` is an explicit readiness opt-in for internal structural validation, not provenance or permission to implement. A type/area/status label for sorting, or `codex` for worker assignment, must not trigger the checklist before joint review. Newly agent-created implementation issues must satisfy full internal standards and carry the readiness label from creation within their existing authorized scope, with their creation receipt. A shared-login issue lacking both a receipt and readiness marker cannot safely be identified as agent-created; workers must obey the creation protocol. That limitation must not turn ordinary human submission back into an internal checklist.

## Review before enrichment

1. The recurring reviewer reads new or meaningfully changed human/unknown-origin issues and existing discussion/decision records. Include Brian's hand-written reports even when they already have internal labels. Do not skip solely because `sefaction`, a bot, `codex` or readiness labels appear. A verified agent-origin issue follows its existing authorized scope instead; it receives no new authority from that classification.
2. Discuss intent with Brian first: problem/request, intended outcome, reproduction or uncertainty, scope boundaries and consequential choices. Offer a short proposed interpretation and focused questions rather than asking him to complete a template. Preserve settled decisions and use their evidence instead of repeating questions. Keep an unresolved request pending review and continue independent authorized work.
3. Once intent is agreed, a worker re-reads the latest issue/comments and enriches it with an implementation-ready current summary: agreed problem/outcome; evidence and limits; delivered work; exact remaining next step; acceptance/completion criteria; and parent/dependency/PR links. Record the actual discussion/decision reference. Unknown evidence stays unknown; do not invent reproduced behavior or acceptance. Keep the original report and history intact. Defer conflicting concurrent edits.
4. Apply correct internal type/status/area dimensions and scope flags, without guessing a blocked choice. Then explicitly add `triage: complete` to activate internal checks; read back edits. Preserve original human/unknown origin. The implementation worker can act only within agreed scope; intent review is not merge/deployment approval. Removing the readiness label returns validation to intake; it does not itself complete work, prove consent or erase provenance.
5. Save reviewed issue identity, meaningful revision and decision reference in the reviewer checkpoint to avoid repeatedly asking about unchanged reports. Substantive changes or missing decisions return to joint review. Structural validation alone cannot establish this decision gate.
