# Recognition catalogue memory

The scanner OCR worker and catalogue reconciliation share an exact recognition catalogue: ordered card IDs, public IDs, names, printed names, face names, set, collector, language and digital status. Refreshing it previously allocated all database rows, transformed cards, a large serialized JSON value and another lookup index alongside the current snapshot. The ordinary67-input source-footer workflow reached the unchanged2GiB OCR limit, with memory reclamation and modest swap but no failed jobs or OOM restart. [#760](https://github.com/sefaction/MTG-Archives/issues/760) records that observation; it does not establish a native OCR leak or a source-footer regression.

The loader now reads512-row pages inside one PostgreSQL REPEATABLE_READ transaction. Concurrent updates, inserts and deletes cannot mix generations across those pages. It incrementally hashes the exact previous canonical JSON representation. If the exact content digest is unchanged, callers retain the existing lookup structures. A changed catalogue receives a new index; counts, timestamps and bulk-import IDs do not substitute for content identity. The transaction closes before index construction/reuse and is bounded to60seconds. Errors propagate without mutating the previous snapshot.

Both OCR and catalogue reconciliation pass their current snapshot to the loader. Native model bytes, image dimensions, OCR/reference geometry, resolver policy, job versions, source/human authority and Inventory behavior are unchanged. Visual and printing workers do not execute this loader and retain their qualified images.
