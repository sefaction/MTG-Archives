# Pricing history tiers and retention gate

The default long-range card view uses observed daily closes for 90 days, weekly closes through two years, monthly closes through ten years, and yearly closes after that. Every weekly, monthly, and yearly row keeps its open, close, low, high, and the dates of those observations. A missing day remains missing. The view labels each point's resolution and plots it at its actual close date. `PRICING_DAILY_HISTORY_DAYS`, `PRICING_WEEKLY_HISTORY_YEARS`, and `PRICING_MONTHLY_HISTORY_YEARS` can change the cutoffs within validated bounds; invalid or overlapping settings fall back to 90/2/10. The short 7/30/90-day drilldown continues to use daily detail.

`price_weekly_summary` and `price_yearly_summary` are rebuildable projections from `price_daily_summary`. Worker refreshes rebuild touched exact printing/provider/finish/type/currency keys, including late corrections, while all raw and daily records remain. Existing installations need a one-time tier backfill after the #328 daily backfill has completed:

```sh
npm run worker:prices:tiers:backfill
```

Run this inside the pricing-worker container (or with the intended `PRICING_DATABASE_URL` and `psql`) after confirming the target. It refuses a stale daily summary, updates both tiers in one transaction, and sets `price_summary_state.tiers_ready` only when complete. Retry is safe. Until then, long-range card history falls back to monthly points. A full `worker:prices:summaries:rebuild` also fills the tiers and marks them ready.

## Local evidence, 2026-09-23

The local pricing database had 1,971,376 raw rows across 41 observed dates from June 30 to September 23 (about 85 calendar days). Raw snapshots occupied 931 MB, daily summaries 747 MB including indexes, and monthly summaries 63 MB. A full custom-format `pg_dump` archive was copied to `.local-data/backups/pricing/mtg-pricing-retention-audit-2026-09-23.dump` (60,724,806 bytes). `pg_restore --exit-on-error --jobs=2` loaded that copied archive into a disposable database. Live and restored databases matched on raw count, date range and price sum; daily count, range and price sum; and 153,875 monthly rows, range and close-price sum. The disposable database was dropped after comparison. The existing primary-app backup does **not** include this separate pricing database; pricing archival needs its own operating path.

The weekly/yearly backfill completed in 177,842 ms on the local snapshot: 650,052 weekly rows (269 MB) and 52,326 yearly rows (21 MB). An isolated corrected-price/repeated-refresh fixture passed. A deterministic sample of 100 weekly and 100 yearly keys compared all open/close/low/high dates and prices plus observation counts to daily source, with zero mismatches. `/login` completed in about 183 ms during the backfill; that is one local concurrency observation, not a production service-level guarantee.

## Deletion gate

The next preservation change adds `price_summary_state.daily_compacted_through` as a recorded boundary for a future daily compaction operation. A touched-key refresh still reconstructs its full daily projection from retained raw snapshots, refreshes scope and weekly/monthly/yearly tiers from that complete projection, and only then removes daily points through the recorded boundary. A local old-date fixture verifies that a later raw correction rebuilds the historical rollups without restoring the compacted daily row. The standalone tier backfill refuses to run after a boundary is recorded; a full raw-backed summary rebuild remains the recovery path. This is a refresh contract, not a compaction job: no cutoff is set and no rows are deleted by this change alone.

## Local daily compaction gate

`npm run worker:prices:daily:compact` reports the proposed cutoff and eligible row count without changing data. Run it in the local web container, where `PRICING_DATABASE_URL` and the mounted `BACKUP_DIR` are available. Its default daily window is 90 days, using the validated `PRICING_DAILY_HISTORY_DAYS` override. It retains the day exactly 90 days before the current database date, and proposes a cutoff one day earlier. A previously recorded cutoff can only advance.

`MTG_LOCAL_PILOT_TEST=1 npm run worker:prices:daily:compact -- --apply` is explicitly limited to the local pricing database. Stop the pricing importer during the operation. Before deleting any eligible daily point, the command checks readiness and raw provenance, writes a full custom-format pricing database archive under `BACKUP_DIR/pricing`, records its SHA-256, restores it into a temporary isolated database, and compares raw/daily counts, dates and price sums plus all tier counts and extrema sums. It then checks that the live source is unchanged, deletes eligible daily points in one guarded transaction, records the boundary, and removes the temporary restore database. The archive, verified-before-delete JSON manifest and applied receipt remain for recovery. If there are no eligible points, the command does not advance the boundary or create an archive.

When `PRICING_RECOVERY_COPY_DIR` is set, daily compaction also publishes a two-file recovery package containing the pre-delete full dump and verified manifest. It copies the package index and both files to that separate destination, reads back their hashes twice, and only then requests the guarded delete. A failed copy stops before deletion. `MTG_LOCAL_PILOT_TEST=1 npm run worker:prices:daily:copy-restore-drill -- --package COPIED_PACKAGE --run` checks the copied package and restores its dump into a disposable database on the configured verification server without reading `BACKUP_DIR`. It compares the restored complete raw, daily and tier statistics with the copied pre-delete manifest. This package represents the state before the whole one-day retention pass, while the raw activation package represents the state after daily compaction.

The final local apply proof used one synthetic January 2026 raw/daily point, a June 25 cutoff, and a 68,760,781-byte archive. The isolated restore matched the live snapshot, including tier extrema sums; exactly one daily row was deleted and an applied receipt was written. A later correction to the retained raw point updated monthly/yearly history while the old daily row remained absent. The fixture and cutoff were then removed, the importer resumed, and raw and daily totals returned to 1,971,376 each. This proof covers daily compaction while raw snapshots remain. Raw-history archival/deletion, incremental archive rotation and a production rollback remain separate #330 gates.

The earlier tier-backfill batch **did not prune raw or daily rows**. The current raw span is younger than the proposed 90-day daily window, so a normal compaction run would currently save nothing. Deleting older raw rows before changing the refresh contract could silently erase older rollups on a later import. The archive drill proved a full copied database can be restored locally; it did not prove incremental archival, per-key correction after raw compaction, or a safe production rollback.

Before raw-history deletion or scheduled retention, a separate reviewed change must preserve archived periods through refresh, explicitly handle late corrections, compact period boundaries without double-counting, support a verified raw restore and rollback, and measure storage and ordinary-site latency on the intended host. No automatic pruning or production scheduling is configured here. Keep issue #330 open until those gates and reviewed raw deletion behavior are complete.

`npx tsx scripts/pricing-raw-retention-plan.ts` is a read-only report against the configured Pricing database. It uses the validated daily-history window (90 days by default), retaining the boundary day and listing the count/date span plus the first 30 older UTC observed days. It also reports total raw table-and-index bytes and whether current summaries match the live source. The output explicitly says `rawDeletionEnabled: false`; it is not a backup, restore proof, archive activation or deletion command. Run it in the local web container with `PRICING_DATABASE_URL` available to size the next archive pilot.

The user selected about 90 days of live raw snapshots and automated older-correction maintenance during 2–5 a.m. America/Chicago. The proposed archive data contract, interruption behavior and activation gates are in [PRICING_RAW_ARCHIVE_DESIGN.md](PRICING_RAW_ARCHIVE_DESIGN.md). This decision does not enable raw deletion or a scheduler.

## Archive-aware refresh basis

The Pricing schema now has a nullable `raw_archived_through` boundary and separate archived scope, monthly, weekly and yearly summary tables. They remain empty until a separately verified archive activation. A touched-key refresh rebuilds its live daily projection, then merges live and archived tier portions by actual observation dates and prices; counts add and tied extrema keep the earlier date. Current/prior price, snapshot count and latest ingest time also combine archived scope metadata with live observations. A live raw row on or before an active archive boundary rejects refresh to avoid double counting. Full summary rebuild enumerates archive-only scopes as well as live raw scopes. The standalone tier backfill still refuses a compacted daily source.

The isolated PostgreSQL fixture exercises a split week/month/year, an archive-only sparse scope, a later live import, overlap rejection and full rebuild. The existing correction fixture also passes against the local snapshot. These checks establish the projection contract, not archive file durability: no archive manifest is activated, no raw row is deleted from the local snapshot, and normal imports have not yet been taught to defer old source observations. Keep #330 open for those gates and off-hours automation.

## Read-only raw segment staging

`npx tsx scripts/pricing-raw-segment-stage.ts --date YYYY-MM-DD` stages one eligible UTC observed day under `BACKUP_DIR/pricing/raw/YYYY-MM-DD`. It accepts only the local Pricing host, requires fresh projections, refuses a day inside the live retention window or an active archive boundary, and caps its uncompressed CSV at 64 MiB so larger days require a separately reviewed split. The command writes an immutable gzip file with all raw columns, reads that file back, restores it into a disposable isolated database, compares exact reserialized rows and count/price totals, then verifies the live day did not change during staging. A JSON manifest records hashes, source revision, range, count, price sum and `verified_staged` status. Temporary CSVs and the restore database are removed; a failed stage removes its incomplete files. The output and manifest explicitly say `activated: false`. This is an archive proof only: it does not populate the archived summary basis, advance `raw_archived_through`, delete live rows or schedule maintenance. The fixture covers one old day, an empty day and rejection of a live day.

## Guarded local raw-segment activation

`npm run worker:prices:raw:activate -- --manifest BACKUP_DIR/pricing/raw/YYYY-MM-DD/segment-....json` checks the oldest eligible staged date without changing the database. The selected date must be older than the live 90-day window, be the minimum remaining live raw date, and already be behind the daily compaction boundary. Stage each subsequent date again after the preceding activation; deleting a segment can change the source maximum ID. A stale manifest is rejected. `MTG_LOCAL_PILOT_TEST=1 npm run worker:prices:raw:activate -- --manifest PATH --apply` is limited to the local Pricing host. Pause the pricing importer before a local apply.

Apply verifies the staged gzip and CSV hashes; makes a new full Pricing database dump; hashes and restores it into an isolated database; compares source state, raw totals and affected visible scope/tier signatures; and simulates the activation and archive-aware refresh on that restored database. It requires identical visible projections after the simulation. Only then does one locked transaction recheck revision, raw count/price total, exact staged-date fingerprint, both compaction boundaries and eligibility. The transaction appends that date's scope and weekly/monthly/yearly archived basis, records the archive and backup hashes in `price_raw_archive_segment`, deletes the verified date's raw rows, and advances `raw_archived_through`. A receipt and full backup remain for local recovery. A failed restore or injected interruption leaves live rows and the boundary intact; retry with a freshly staged segment when source state changes.

The isolated PostgreSQL fixture activates two old dates (including an archive-only sparse scope), proves an interrupted restore leaves live rows intact, and checks refreshed visible history plus full rebuild. This is a **local pilot**, not an active retention job: no scheduler, production deletion, external archive-file backup verification, or archived-feed correction automation is enabled. Keep #330 open until those operations and a measured normal-site resource budget are verified.

## Archived feed deferral

After a raw boundary is active, the regular MTGJSON importer compares the feed's canonical identity/price fingerprint once per archived UTC date with the activated segment's stored fingerprint. An unchanged date needs no database lookup per card and creates no spool file. A changed or newly supplied old date is written as a bounded gzip feed spool under `BACKUP_DIR/pricing/feed/YYYY-MM-DD`, with hash, count, source job and `PENDING` queue row in the Pricing database. A replay of the same fingerprint is deduplicated. The importer processes only dates newer than `raw_archived_through` as live raw, refreshes only their scopes and publishes only their current prices. Its upsert transaction checks the expected boundary under a lock, so a concurrent activation cannot silently reinsert old history. Missing archived source days are counted as anomalies and do not cause deletion.

This protects ordinary imports after activation, but a pending archived correction is **not yet applied**. Do not activate a live retention schedule until the off-hours worker verifies queued feeds against the archived generation, rebuilds affected summaries and replacement archive files, and provides retry/lease/alert behavior. The Pricing worker now mounts the backup directory for durable spooling; disk and backlog limits still need acceptance testing.

## Archived daily correction basis

Each activated raw date now contributes one compact `price_archived_daily_basis` row per exact printing/provider/finish/type/currency/day. It retains the chosen price and snapshot provenance plus that date's raw count and latest ingest time. Normal app requests still read the scope and weekly/monthly/yearly projections; this basis is for off-hours repair. `rebuildArchivedSummariesSql` reconstructs those archived projections for touched scopes from the basis, including open/close/low/high dates, counts, current/prior prices and latest ingestion. It refuses to erase a preexisting archived scope that has no basis, which can occur if older activation code ran before this table existed; its raw segment must be restored first.

The isolated PostgreSQL fixture shows the rebuilt archive projections match the incrementally activated projections exactly. It then changes one old basis price and adds one previously absent old identity, rebuilds archived and visible projections, and checks corrected extrema and the new sparse scope. This is a reconstruction proof, not a queued-feed apply: immutable raw segment generation replacement, feed reconciliation, transactional revision/receipt update, scheduling and measured storage remain #330 work.

## Local queued archived correction pilot

`npm run worker:prices:raw:correct -- --date YYYY-MM-DD` is a read-only plan for the newest pending feed for one archived UTC date. It verifies the queued gzip hash and canonical identities, reads the active raw segment if one exists, and reports corrected, newly added, unchanged and missing source identities. Missing source identities remain archived; an incomplete feed never deletes them. `MTG_LOCAL_PILOT_TEST=1 npm run worker:prices:raw:correct -- --date YYYY-MM-DD --apply` is restricted to the local Pricing host and processes at most 500 changed or added identities per run. A larger feed remains pending with a durable applied count; each later run reconciles against the activated generation and processes the next 500 differences.

The apply command makes and hashes a full Pricing database backup, restores it into a disposable database, restores the current date segment there, applies feed corrections and additions while preserving unchanged and missing raw rows, writes a new immutable gzip generation, restores that written file, and compares every raw column with the staged rows. It simulates one locked transaction on the disposable database. After rechecking live source state, file hashes and affected visible projections, the same transaction on live Pricing updates archived daily basis, rebuilt archived and visible summaries, the active segment generation, source/summary revisions and queue status. The old generation is retained. A filesystem receipt records the committed generation. Interruption before activation leaves the queue pending and the previous generation active; replay after success finds no pending generation. The isolated fixture exercises both cases, a new old-date segment and corrected extrema.

This remains a local pilot. It has no active scheduler, external backup copy proof, measured app latency or full rollback drill under load. These gates must pass before automatic raw deletion or unattended corrections. A feed with no price changes settles without rewriting the archive; if it omitted archived identities, it records `SOURCE_ANOMALY`, preserves those identities, and stops automatic retries until a new feed generation arrives. A partially applied feed that omitted identities records `APPLIED_WITH_MISSING` when its changed rows finish. Both statuses remain visible in the maintenance backlog. The app's local backup directory is not an independent recovery destination; the existing Unraid backup job covers the live paths and verifies its weekly tarballs, but a time-matched independent copy and restore proof are still required.

## Recovery integrity audit

`npm run worker:prices:archive:audit` reads all active raw segment and pending-feed metadata. It checks that each referenced file stays inside `BACKUP_DIR/pricing`, hashes active gzip archives, verifies their decompressed CSV hashes, and hashes the full Pricing backups and pending feed spools. It reports segment/feed counts, stored bytes and up to 30 failures; any failure exits nonzero. This is a local-file integrity check, **not** proof that the existing backup service copied the files or that a database restore works. The isolated PostgreSQL fixture restores a pre-correction full backup into a separate database after applying a historical correction and confirms the old generation, pending feed, original visible price and revision state return. It never overwrites the running Pricing database. A full-size rollback and off-site read-back drill remain before unattended maintenance or raw deletion.

`MTG_LOCAL_PILOT_TEST=1 npm run worker:prices:archive:restore-drill -- --run` makes a full custom-format dump of the local Pricing database, SHA-256 hashes it, restores it into a disposable PostgreSQL database, re-hashes the dump and compares raw, all visible/archive tier counts and price totals, queue/segment counts and summary state before/after. It reports dump size, restored database size and dump/restore durations. Pause the local Pricing importer first so the before/after comparison is stable; the command itself does not stop workers or replace the live database. ## Existing Unraid backup evidence

Read-only inspection on 2026-09-26 found the Unraid Appdata Backup plugin configured for a weekly Monday 00:00 run. It reads `/mnt/user/appdata` and writes to `/mnt/user/File Share/appdata backup/`. The source `appdata` share uses the cache pool; the destination `File Share` uses the array. The September 21 run's log lists `/mnt/user/appdata/mtg-archive/pricing-postgres` for the Pricing PostgreSQL container and `/mnt/user/appdata/mtg-archive/backups` for the web/backup containers. Corresponding MTG Archives tarballs are present in that run's directory, and the plugin reports successful verification of each archive. The job is configured to verify backups by default.

This is a weekly copy to another pool on the same Unraid host. The plugin's verification is archive integrity, while the historical restore drill below checks a database from that destination. No off-host copy has been demonstrated, and a weekly job cannot prove that a newly written raw segment or correction backup was copied before a daily deletion or correction. Do not copy live PostgreSQL data files while the database is running; use the verified application archive files and a consistent full Pricing dump for the correction workflow.

## Optional verified per-operation recovery copy

An enabled `pricing-archive-maintenance --apply` runner now requires `PRICING_RECOVERY_COPY_DIR` to resolve to an existing directory separate from `BACKUP_DIR` before it even reports backlog or claims the lease. The target must be mounted into that runner's container; simply setting a host path in the environment does not mount it. Each correction still verifies its actual copied archive and dump before the live transaction. The read-only `--once` backlog report works without a copy target. The optional Compose profile remains disabled.

The local raw activation and archived-correction pilots can use `PRICING_RECOVERY_COPY_DIR` to name a separately mounted, existing destination directory. After their full Pricing dump has passed isolated restore and their immutable raw segment has been verified, they copy the archive, dump, stage manifest, pre-operation backup manifest and a small relative-path package index into the destination, preserving their paths below `BACKUP_DIR/pricing`. Each copy is written under a unique temporary name, flushed, published without overwriting an existing generation, and SHA-256 hashed from the destination. All five files are read back again immediately before the live Pricing transaction. A missing, corrupt or unreachable destination stops that operation before any live raw deletion or correction; completed receipts record the destination paths and hashes. Repeated reads accept identical existing copies and refuse changed ones.

For a completed local activation or correction receipt with those five copied files, run `MTG_LOCAL_PILOT_TEST=1 npm run worker:prices:archive:copy-restore-drill -- --receipt /app/data/backups/pricing/raw/YYYY-MM-DD/RECEIPT.json --run` with `PRICING_RECOVERY_COPY_DIR` mounted into the container. The drill verifies copied archive, dump and manifest hashes, decompresses and hashes the raw CSV, restores the **destination copy** of the full dump into a disposable local Pricing database, compares raw totals and source revision with the pre-operation manifest, then removes that disposable database. It does not replace or pause the live database. The copied files and original receipt remain; a real loss of the source backup directory and a full operational recovery procedure are separate gates.

If the source backup directory is unavailable, run the same local drill with `--package /mounted/recovery/pricing/OPERATION.package.json --run` and `PRICING_RECOVERY_COPY_DIR` pointed to the copied package root. This mode needs no `BACKUP_DIR` or original receipt: it validates all four indexed destination files, then restores the copied dump into a disposable database. The isolated fixture temporarily hides the entire source backup directory and passes this drill for archive activation; it also drills an older correction package. The command is a recovery-readiness check, not an automated replacement of the live database. A real restore from the selected Unraid destination and its host mount still needs verification.

`npm run worker:prices:archive:copy-audit` quickly checks every published `*.package.json` at the `PRICING_RECOVERY_COPY_DIR` root and hashes its four indexed files without connecting to Pricing or reading `BACKUP_DIR`. It prints the checked, verified and failed counts plus up to 30 failure details, and exits nonzero if any package is incomplete or changed. This is useful before a restore drill and after copying to the chosen destination; it does not itself restore a database or prove the destination is off-host.

When the optional archive-maintenance runner is explicitly enabled, it uses its database lease during the 2–5 a.m. Central window to remove recovery-copy `*.partial-UUID` files older than seven days. It scans once per runner process and reports eligible files, removed files and bytes. It matches only the copy writer's temporary names, including nested raw segments; published files and recent partial copies are untouched. This handles a process terminated during copying without requiring regular manual cleanup. The disabled profile performs no cleanup.

The local Compose overlay now mounts `.local-data/pricing-recovery` into the web and optional archive-maintenance containers at `/app/data/pricing-recovery`, separate from `/app/data/backups`. This is a local pilot on the same laptop drive, not independent recovery. For an operator-provided destination, include `docker-compose.pricing-recovery.yml` and set `PRICING_RECOVERY_COPY_HOST_PATH` to an **existing** host mount. The override refuses an unset path and prevents Compose from silently creating a missing one. Confirm the mount resolves to the chosen separately protected storage, run the read-only package audit and a copied-package restore drill, then review the backup and load gates before enabling maintenance or raw retention. Merely adding the override does not start the optional maintenance profile.

This is an optional local pilot until the Unraid array destination is mounted into a dedicated maintenance container and tested there. It does not enable the scheduler or bypass `MTG_LOCAL_PILOT_TEST=1`. The app's weekly Appdata Backup job remains a separate backstop. A successful copy to the same Unraid server is not off-host recovery, and a restored Pricing database plus raw archive from that destination must still be drilled before automatic retention or unattended corrections are enabled.
