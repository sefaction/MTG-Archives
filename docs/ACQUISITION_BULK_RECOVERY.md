# Bulk confirmation response recovery

Issue [685](https://github.com/sefaction/MTG-Archives/issues/685) concerns an interrupted response after a successful bulk review save. The page previously displayed a failure, continued later writes, and missed the saved-selection handoff to Inventory. [PR687](https://github.com/sefaction/MTG-Archives/pull/687) depends on individually unapproved PR684's exact displayed-proposal attribution and requires its own approval.

The browser freezes each selected request before writing: original printing, language, finish, condition, revision and displayed evidence identity. It retries a transport failure once with the identical JSON body, rechecking browser draft protection. Each attempt has a 15-second transport timeout. HTTP rejections are never retried. The existing server exact-replay fence acknowledges an already saved identical review without creating another revision or correction event, and rejects a changed review or actor.

If both responses are interrupted, or a new browser correction blocks recovery, later confirmations pause. **Continue original confirmations** retains the original requests across **Back to card list** and later default changes. Pending rows show their original finish and condition. Proposal reload and new bulk selections are disabled until that queue resolves. New drafts must be saved or cancelled; a changed server review returns its conflict without being overwritten. Navigation away discards the in-memory queue and stops further automatic sends; server reviews remain authoritative when reopened. No cross-reload automatic confirmation is introduced.

This saves reviews only. Inventory still requires its separate explicit confirmation. Sampling, retention, verifier roles, native workers, schema, server replay policy and recognition training are unchanged. Existing 64 decimal GB per owner and 2% controls remain.
