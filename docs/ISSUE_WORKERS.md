# Two-node issue workers

Brian's October 23, 2026 request is to keep the laptop and desktop working through
issues throughout the day. This corrects the earlier blanket product-area split
and the assumption that a saved desktop setup document established a schedule.
It does not grant automatic merges, production changes or scanner operation.
GitHub owns live issue/PR state; local scheduler state and observed executions
establish whether a worker is actually configured and running.

## Shared queue and ownership

Both nodes may take an agreed, unclaimed issue that fits their actual tools,
data, memory and storage. Prefer the laptop for Inventory/storage/browsing and
phone usability, and the desktop for larger backend, acquisition, recognition,
pricing and recovery work. These are preferences, not permanent prohibitions.
A small shared/backend change required for a coherent owned fix does not by
itself require another human permission round.

Explicit issue assignments and active owners remain binding. In particular,
Brian's decision to keep the Public Language-filter repair #913 with the desktop
remains in force; a general queue correction does not silently transfer it.
Respect a resolving PR's current owner and dependencies. Existing historical
product-area notes do not reserve every unclaimed issue in an entire area.

Before implementation, read the latest issue, comments and relevant PRs, record
one concise claim with node, actual owner, branch and bounded scope, then reread
before overlapping writes/publication. Keep detailed host/run/resource identities
in the private checkpoint where public exposure is inappropriate. GitHub comments
and labels are advisory, not distributed fencing. Conflicting or uncertain claims
defer that batch while the node selects independent work. Never steal a claim
because its chat is idle or its timestamp is old.

## Selection loop

1. Finish the node's actual owned live work, interrupted coherent batch or
   actionable review feedback. Reconcile process/CI handles and handoff evidence;
   a checkpoint alone does not establish a live operation or terminal state.
2. Honor Brian's explicit priorities and urgent integrity/security defects.
   Otherwise take the oldest agreed human bug/feature with resolved dependencies
   that the node can perform. Use creation time, not latest automated activity.
3. Reuse recorded intent and decisions. A missing internal template, label or
   optional reproduction detail is not a new approval gate. Follow ISSUE_INTAKE.md
   for human/unknown-origin intent; ask only a material unresolved question and
   continue independent work while the answer is pending. Never invent origin.
4. Check the whole shared queue before concluding that the preferred area is
   exhausted. Capability or access can exclude a particular operation, not all
   source work or smaller checks in that product area.
5. When an implemented PR awaits independent review or Brian's merge approval,
   preserve its review environment/evidence and select the next independent
   issue. Perform a useful independent review of another author's ready PR when
   appropriate. Do not call a review of one's own work independent review.
6. A historical incident awaiting actual failing inputs remains open with its
   precise missing evidence. Select another item rather than repeating unchanged
   synthetic positives or pretending that non-recurrence diagnoses history.
7. If no eligible implementation or review remains, perform only a bounded audit
   of a concrete unmet workflow requirement or risk. Record the question, next
   test and stopping criterion. Fix demonstrated defects; do not manufacture
   speculative tickets or continuously expand qualification to keep busy.

A node-wide blocker requires a current queue assessment showing why every
available candidate is owned, materially ambiguous, dependency/access blocked or
already review-ready. Report the specific external action needed. One waiting PR,
one declined assignment or one temporary resource conflict is insufficient.
Scheduled workers remain configured for future runs; do not disable them merely
because one run has no eligible item. Persistent-goal blocked rules remain those
of the host application; bookkeeping alone is not progress.

## Execution and verification

Use an isolated current-main feature branch/worktree and one coherent
implementation batch per node at a time. A scheduling/policy coordinator may own
its separate configuration files without taking an implementation worker's batch
or runtime. Preserve root WIP and other owners' files.

Each node builds/tests its own changes when needed. Before heavy work, inspect
actual resources and workloads, use the host's supported exact-owner runtime
guard and a measured/conservative task envelope. Serialize heavy work on that
host/resource; a local guard is not a cross-machine lock. Keep distinct required
pipeline stages and durable work safe. A blocked build can leave a draft PR while
source checks or another independent task proceeds.

Start with focused meaningful tests, broaden for actual shared/schema/privacy/
integrity/concurrency risk, retain required exact-head CI and affected desktop/
phone runtime checks. Reuse evidence whose inputs and assumptions still match.
Independent review does not automatically require another costly build. Apply
the existing cleanup/retention rules and release exact-owned locks only after
children are terminal. Never bypass integrity, permissions or approval to improve
throughput.

Deliver a concrete fix, evidence and one PR per coherent batch. Resolve feedback
and mark ready only when applicable gates actually pass. Then continue the queue.
Merge only after explicit individual approval and a merge request; close resolved
issues after the resolving merge, preserving history and every genuine remainder.

## Scheduling and handoff

Use one standalone local implementation automation per node, not duplicate jobs
or substitute cloud reminders. The intended cadence is hourly: laptop at minute
00 and desktop at minute 30, America/Chicago with daylight-saving handling. Keep
the existing configured model/reasoning unless Brian requests a change or the
configured model is unavailable. The separate approval roundup stays read-only.

Each run should use its useful work window, continue to another eligible item
after a clean handoff when time permits, and stop starting substantial new work
near its planned end. An owned live build/test must finish or have a supported
continuing handoff; a timer never authorizes cancelling it, dropping its lock or
starting overlapping replacement work. A successor finding a verified live
worker records that the node is busy and avoids duplicate implementation.

At handoff record current branch/head, issue/PR, actual owner/children, completed
and pending checks, item-specific blockers and the next eligible action. Keep
current review/rollback resources and compact failure evidence; retire only
verified owned superseded resources. Do not spend every run recreating unchanged
status documents.

Verify the saved automation ID, full prompt, local project/host, cadence, status
and next run through supported tools/UI, then inspect an actual execution.
Prepared text is not an active scheduler. A routing failure needs concrete
diagnosis and the smallest supported repair; do not edit internal app databases
or claim project membership makes a cloud chat local. Preserve and complete
independent work while a particular host access step is unresolved.

Both computers must be powered on, awake, online and running the desktop app for
local work. The scheduler cannot guarantee execution while its host is offline.
